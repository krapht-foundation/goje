# RFC 0016: M15 - Audio mixing, vision, and platform reach

**Status:** Implemented in milestone 15. The delivered milestone differs from this proposal in the ways listed under [Implementation notes and results](#implementation-notes-and-results); where they differ, the specifications are the contract.

## Problem and goal

[M14](0015-m14-text-rts-commands-and-replays.md) produced the outpost, a battle with a menu, a HUD, group commands, saves, and replays. Three gaps now stand between it and a game that someone else can install and play.

1. The outpost is silent. [M11](0012-m11-audio-and-sound-maker.md) plays one prepared cue at a time, and a new cue replaces the one that is playing. A fight with bolts, hits, deaths, an alarm, and menu clicks needs overlapping sounds, and a sound that comes from a place on the board should sound as if it does.
2. Everyone sees everything. Every scout knows where every guard stands, and a guard knows where every scout is within six tiles through a wall. A wall cannot hide anything, so scouting, ambushes, and surprise, which are most of what makes a small real-time battle interesting, do not exist.
3. The game runs only where a developer can start it. Touch and gamepad input do not exist, so a phone browser or a couch cannot drive the outpost. There is no command that turns a Goje game into something to hand to a player: a web folder, a macOS application, or a Linux archive.

A developer should be able to play the outpost with a mouse, a finger, or a gamepad; hear bolts, hits, and an alarm that come from where they happen; scout a board in which walls hide guards and unexplored cells are dark; and run one command on a game to get a web bundle and a package for the host's desktop operating system, with checksums, that CI can publish. Desktop and web must still agree exactly on everything that the simulation decides.

This milestone combines the three options that [RFC 0015](0015-m14-text-rts-commands-and-replays.md#next-milestone) left open. They share one scenario, the outpost, so they are delivered as ordered slices and committed once, as M13 and M14 were. A following milestone, [M16](#next-milestone), takes what remains.

## Decisions for review

| Decision | Recommended | Alternative and tradeoff |
| --- | --- | --- |
| Delivery | Input first, then the mixer, then vision, then the outpost that uses all three, then the build and release command. Each slice has its own headless tests and exit check, and the milestone is committed and pushed once, at the end. | Split platform reach into M16. M15 is then smaller to review and the release command can wait for a more settled game, but touch and gamepad are needed by the outpost slice, and a game that nobody can install is the main gap. The input fields stay in M15 either way. |
| Mixing | A voice pool with gain and stereo pan per voice, 16 voices, and a documented equal-power pan law. Native hosts mix in Go inside the device callback they already own. Browsers build a Web Audio graph of a buffer source, a gain, and a stereo panner for each voice, which the Web Audio specification defines with the same law. A Chromium check compares the rendered output of both with a tolerance. | Mix in Go on both targets and stream the result to an `AudioWorklet`. The output would be identical and the mixer would be tested once, but it adds a worker, a shared ring buffer, and latency of a few buffers on web, and a Go WebAssembly program cannot run inside a worklet. |
| Spatial sound | A pure function turns a source position and a listener position, both in logical screen pixels, into a gain and a pan. The game calls it and passes the result with the cue, so Goje does not need to know what a camera or a world is. | A listener object in the engine that reads the camera. It is less code in games, but it ties audio to one view model and to floating-point state that the engine would own. |
| Voice policy | The host owns a fixed pool and, when it is full, replaces the oldest voice. The game decides what is too frequent: the outpost plays at most one voice per cue every three ticks. | A priority and cooldown table in the engine. It protects naive games, but it fixes a policy before a second game shows which one is general. |
| Sound and replays | Sound stays output. A replay records input and plays it again through the same scene, so playback sounds like play, and a nested runtime forwards its parent's sound output through a new `Tick.Sound` method. | Record cues in the replay. Playback would not depend on the scene, but the format would carry output and a changed mix would invalidate old recordings. |
| Vision | A package `engine/vision` computes line of sight on a grid with symmetric shadowcasting in integer arithmetic. The skirmish simulation gains vision as an option that is off by default, so the M13 and M14 traces do not change. The outpost turns it on and changes its content check string, which retires its old replays and saves. | Always on. Every skirmish test, trace, and benchmark would change, and the M13 contract would be redefined silently. A rule of this size belongs in a new, named content version. |
| What walls hide | Only wall cells block sight. A deck is a raised solid that units walk beneath and it does not block sight. A unit sees every cell within seven cells whose line of sight is clear. | Height-aware sight. It is more faithful to a 2.5D board, but it needs a rule for what a raised solid hides at each height, and no scenario needs it yet. |
| Fog | The scouts' team remembers which cells it has seen. A cell is unexplored, explored but out of sight, or in sight. Enemies are drawn only in sight. Walls and ground are drawn only where explored, and out-of-sight cells are dimmed. The alarm keeps its M13 meaning: it wakes every guard, who then hunt without needing sight. | Draw remembered enemies as ghosts. It is friendlier, but it needs a rule for how long a memory lasts and a second state to record and hash. |
| Touch | The first finger on the screen drives the existing pointer fields, so a tap is a click and a drag is a drag. All fingers, up to five, are also reported in a new field. The host does not turn long presses or pinches into gestures. The outpost adds on-screen command buttons for what the right mouse button and the keys do. | Synthesize a right click from a long press in the host. It makes old games work, but it adds a delay and a guess to every first finger, and games that want a long press cannot have it. |
| Gamepad | Up to four pads with the standard layout, reported with buttons as a bit set and sticks and triggers as small integers after a deadzone. Browsers use the Gamepad API and desktop uses GLFW's gamepad state. Neither host turns a pad into keys. The outpost moves a cursor with the left stick. | Report raw axes as floats. Floats record and compare poorly: a stick that rests at 0.003 would end every run of identical ticks in a replay and would make recordings several times larger. |
| Recording the new input | The new input fields are recorded with new flag bits in the existing replay format. A recording that uses none of them is byte for byte what it was. | A format version 2. It is cleaner to state, but no released tool reads version 1, and every pinned byte sequence in the tests would change without a reason. |
| Build command | A new `cmd/goje` with `build` and `package`. `build` makes a web directory and a desktop executable of the host's platform. `package` makes archives and checksums. They take flags for the name, version, and icon, and do not add a new manifest. | Add fields to `goje.json`. The project format is validated strictly and read by the games, and release data is not game data. |
| Native targets | The host's own operating system only, because the desktop host uses cgo for the window, OpenGL, and audio. CI builds each supported system on its own runner. The macOS package is an unsigned `.app` bundle and the Linux package is an archive with a `.desktop` file. | Cross-compile with a C toolchain per target. It is possible but fragile and needs graphics headers for each system, and the CI runners already provide the systems. Signing, notarization, installers, and Windows are not attempted. |

## Proposed design

### Input: touch and gamepad

- `engine.Input` gains `Touches [MaxTouches]Touch` and `Gamepads [MaxGamepads]Gamepad`, with `MaxTouches` of 5 and `MaxGamepads` of 4. A `Touch` has a nonzero ID that is stable while the finger is down, a position in logical pixels, and an `Active` flag; inactive entries are all zero so that `Input` stays comparable and a run of identical ticks stays one run. Touches are listed in the order the fingers landed. A finger beyond the fifth is ignored.
- The first finger drives the pointer fields exactly as the mouse does: its landing is a `PrimaryPress`, its movement moves the `Pointer`, `PrimaryHeld` is true while it is down, and its lifting is a `PrimaryRelease` at its last position. If a second finger lands, the first keeps the pointer. If the first lifts while another is down, the pointer ends its drag with a release and the other fingers appear only in `Touches` until all have lifted. Focus loss clears every touch without a release, as it does for the mouse.
- A `Gamepad` has a `Connected` flag, a `Buttons` bit set, and integer axes. The buttons follow the W3C standard layout: the four face buttons, the shoulders, the back and start buttons, the stick presses, and the four directions, 16 in all. `LeftX`, `LeftY`, `RightX`, and `RightY` are `int8` values from −127 to 127 with up being negative, and `LeftTrigger` and `RightTrigger` are `uint8` values from 0 to 255. The host applies a circular deadzone of 15% to each stick, rescales the rest to the full range, and rounds, so equal positions give equal bytes on every target. A pad with no standard mapping is reported as disconnected.
- The browser host reads `navigator.getGamepads()` once per frame and handles Pointer Events with the `touch` pointer type, calling `preventDefault` and setting `touch-action: none` on the canvas so that the page does not scroll or zoom. Desktop reads `glfw.Joystick.GetGamepadState` for the first four joysticks that have a standard mapping. Desktop has no touch input, because GLFW has none, and says so in its documentation.
- `ui.Menu` and `ui.Button` learn the new input so that a menu works with a pad without scene code: the up and down directions and the left stick move the selection, the south face button activates, and the east face button cancels. Their results keep their types.
- `specs/runtime-m1.md` documents the fields and the host rules. The replay format records them with new flag bits; see [Replays](#replays-and-the-new-input).

### Audio mixing

- `engine.SoundOutput.Play` takes a gain and a pan: `Play(cue int, gain, pan float32)`. `Tick.PlaySound(cue)` stays and means a gain of 1 and a pan of 0. `Tick.PlaySoundAt(cue int, gain, pan float32)` is new, and `Tick.Sound()` returns the output so that a parent scene can give it to a nested runtime with `SetSoundOutput`. The change to the interface is a clean cutover: the queue is the only implementer in the repository.
- `audio.Spatialize(listenerX, listenerY, sourceX, sourceY, hearing float64) (gain, pan float32)` returns a gain that falls linearly from 1 at the listener to 0 at `hearing` pixels and a pan that is the horizontal offset divided by half of `hearing`, clamped to −1 and 1. It is pure and allocation free, and games choose what the coordinates mean.
- `audio.Mixer` is a pure Go voice pool. It holds up to 16 voices, each a reference to a clip, a position, a gain, and a pan. `Start` takes a voice, replacing the oldest when the pool is full. `Render(dst []float32)` mixes interleaved stereo frames at 48 kHz by adding each voice's samples scaled to `gain × cos((pan + 1) × π/4)` on the left and `gain × sin((pan + 1) × π/4)` on the right, which is the equal-power law that the Web Audio `StereoPannerNode` uses for a mono source, advances the voices, drops those that have ended, and clamps the sum to −1 and 1. It allocates nothing after creation.
- `internal/sound.Queue` carries a gain and a pan with each request and grows to 64 requests. The M11 rules stay: enqueueing never blocks, allocates, or calls a device, requests are dropped before the device is ready and after a clear, and focus loss, suspension, and scene exit clear every pending request and stop every voice.
- The desktop host runs the mixer inside its existing device callback, which drains the queue into `Mixer.Start` and then renders. The browser host keeps one `AudioBuffer` per clip, as it does now, and for each request starts a source through a gain node and a stereo panner node into the context's destination, counting voices so that it never has more than 16 and stops the oldest first. Both log availability and failures outside the hot path, as M11 does.
- The outpost bank grows from the one M11 sound to about eight: bolt, hit, fall, alarm, click, victory, defeat, and an order acknowledgment. They are made with the Sound Maker's synthesis from checked-in settings, and a test regenerates them and compares the bytes, so the assets cannot drift from their source.
- The simulation reports what happened. `skirmish.Sim.Events` returns the events of the last `Step` in a slice that the next step reuses: a bolt fired, a bolt hit, a unit fell, and the alarm sounding, each with the unit and the ground position. Events are output. They are not in the trace, the hash, or a snapshot, and reading them does not change the simulation. The scene turns them into cues with `audio.Spatialize` from the camera's view, at most one voice per cue every three ticks, and a mute key and a volume setting scale the gain. Neither the mute nor the volume is recorded, because they do not change the match.

### Vision

- `engine/vision` has one function, `Cast(origin grid.Cell, radius int, blocked func(x, y int) bool, visit func(x, y int))`, which calls `visit` once for each cell within `radius` cells of the origin, by the test `dx² + dy² ≤ radius²`, that is in line of sight, in a fixed order. It uses symmetric shadowcasting with slopes as integer fractions, so the result is the same on every target and is symmetric: if a sees b, then b sees a. A blocked cell is itself visible, as a wall is seen from in front. The origin is always visible. Cells outside the grid are blocked.
- A `vision.Field` holds a count of how many viewers see each cell and the cells each viewer saw last time. `Move(viewer, cell)` removes the viewer's old cells, adds the new ones, and keeps the counts, and `Remove(viewer)` takes a viewer away. It does its work only when the viewer's cell changes, so a still army costs nothing, and it never allocates after it is created and sized.
- `skirmish.Sim` gains `EnableVision(cfg VisionConfig)`, which takes the sight radius, and which must be called before the first `Step`. With vision off, which is the default, nothing about the simulation changes and every M13 and M14 trace is reproduced. With it on:
  - each team has a `Field`, and a unit moves its viewer when its cell changes and removes it when it falls;
  - the scouts' team also has an explored set that only grows;
  - a unit fires at, and an attack-move stops for, an enemy only while that enemy's cell is in its team's sight;
  - an `Attack` order needs a target in sight when it is given, follows the target while it stays in sight, and goes to the last cell it was seen in if it leaves, where it ends as other orders do;
  - a guard wakes when its team sees a scout, instead of when a scout is within six tiles, and still wakes for the alarm, after which it hunts without needing sight, as in M13;
  - `Visible(team, cell)` and `Explored(cell)` report the state for drawing and tests.
- The snapshot gains the explored set. Visibility is recomputed from the restored units, so a restored simulation has the counts of the one that was saved. The trace and the outpost's state hash include the explored set.
- The outpost draws fog. Ground is not drawn in unexplored cells, and it is dimmed in explored cells that are out of sight by a tinted draw of the ground region in a dark color. Walls and the deck are drawn in explored cells, and guards and their bolts only in sight. The top bar shows the guards in sight instead of every guard, and the result of a match is still decided by all of them. A mixed fog and sound check is part of the smokes: a guard behind a wall is not drawn, and the bolt that hits a scout is heard before the guard is seen.

### Replays and the new input

- `replay` records the touches and gamepads with two new flag bits in the run header. A run whose input has no active touch and no connected pad has neither bit, so every recording made before this milestone, and every recording that does not use the new fields, has the bytes it had. Touches are stored as a count and then an ID and two exact position values for each, and a pad as its index, buttons, six axis bytes, in that order. The decoder rejects counts beyond the limits before it allocates from them, rejects an inactive entry in a list, and rejects a pad that is listed twice.
- `specs/replay-v1.md` keeps its version number. The change is recorded in the specification and in the RFC, and the tests pin the bytes of a run that uses the new fields in addition to the old pinned bytes.
- The outpost's state hash and snapshot include its new state: the touch and gamepad cursor, the explored set, and the command mode of the on-screen buttons. Its content check string becomes `outpost-2`.

### The outpost

- Fog, sound, touch, and gamepad apply to a new revision of the outpost, `outpost-2`. The skirmish stays as it is, with its traces. The outpost's old traces are retired and replaced by new pinned values for the recorded fight, which have to be the same natively and under WebAssembly.
- With a pad, the left stick moves a cursor, the south button is the primary click, the east button is the secondary click, the west button arms an attack-move, the north button holds fire, the bumpers cycle through the groups, and start pauses. With touch, a tap and a drag act as the mouse does, and a row of buttons at the bottom of the screen, which appears after the first touch, offers Move, Attack-move, Hold, and Focus for what the right button and the keys do. A mouse still works and hides the buttons again.
- The level and its Level Builder round trip stay as they are.

### Build and release

- `cmd/goje build [-o DIR] [-name NAME] [-version V] [-tags TAGS] [-icon PNG] [PACKAGE]` builds the main package, which is the current directory by default. It writes `DIR/web/` with `index.html`, `game.wasm`, `wasm_exec.js`, a web manifest, and icons, and `DIR/desktop/GOOS-GOARCH/` with the executable, which is a `.app` bundle on macOS. The page is the generic shell that the Beacon and the playground pages share: one canvas, the Go runtime started once, and an error message if WebAssembly or WebGL 2 is missing. The build uses `-trimpath`, `-buildvcs=false`, and `-ldflags=-s -w`, so that the same sources give the same binaries.
- The web build is possible on any machine. The desktop build runs only on the host system, and `-target web` and `-target desktop` choose one of them. Asking for an unsupported system gives an error that says why. The tool checks that the Go version is the module's and that the `goje.json` of the game, if the directory has one, passes `project.Load`.
- `cmd/goje package` runs `build` and then writes `DIR/release/` with `NAME-VERSION-web.zip`, a `NAME-VERSION-GOOS-GOARCH.tar.gz` that holds the `.app` bundle or the Linux executable with a `.desktop` file and the icon, and `SHA256SUMS`. Archive entries are sorted, have fixed times and permissions, and carry no user names, so packaging twice gives identical files.
- The macOS bundle has an `Info.plist` with the name, the version, a bundle ID that comes from `-id` or from the name, a high-resolution flag, and the category for games. The icon is a 512 × 512 PNG that the tool wraps in an `icns` file. It is not signed, so macOS asks the player to allow it once.
- `.github/workflows/release.yml` runs on a manual request and on tags that start with `v`. A matrix of an Ubuntu runner and a macOS runner builds and packages the playground and Beacon, uploads the files as workflow artifacts, and, for a tag, attaches them to a draft release together with a combined checksum file. A manual run publishes nothing.
- Mobile browsers get a viewport that does not zoom, a canvas that fills the screen with safe-area padding, and a web manifest, so that a game can be added to a home screen. A service worker and offline play are not part of this milestone.

### Allocation and budget

- The mixer's `Render`, `Spatialize`, vision updates after the field is sized, the HUD, the fog draw, and the new input conversion in both hosts allocate nothing in steady state. Tests with `testing.AllocsPerRun` check each of them that can run headlessly.
- A benchmark mixes 16 voices into a 512-frame buffer and reports the time per buffer, which has to be well below the 10.7 milliseconds that the buffer lasts, natively and as WebAssembly under Node.
- The skirmish benchmark gains a vision mode on the 64 × 64 board with 256 units, with a group-order variant as in M14. The worst tick still has to stay under half of a 60 Hz frame on the development machine, or the cost is reported and a cheaper update, such as recomputing a viewer's cells every second tick, is chosen and recorded.
- A fog frame is drawn with at most one image per cell, so the outpost's 99 cells need fewer than 100 extra calls.

## Out of scope

Music, streaming, compressed formats, per-voice pitch, reverb, and an audio editor beyond the Sound Maker. Windows, Android, and iOS applications, code signing, notarization, installers, auto-update, an app store, and a service worker. Touch on desktop, rumble, gamepad remapping and non-standard pads, and text input. Height-aware sight, remembered enemies, vision for the guards' explored cells, and fog in the Level Builder. Networking, which is the likely use of the replay and hash machinery and gets its own milestone.

## Implementation notes and results

The accepted behavior is recorded in the [runtime](../specs/runtime-m1.md), [replay](../specs/replay-v1.md), [audio mixer](../specs/audio-mixer-m15.md), [vision](../specs/vision-m15.md), [skirmish](../specs/skirmish-m13.md), [outpost](../specs/outpost-m14.md), [playground](../specs/playground.md), and [build](../specs/build-m15.md) specifications and in the [audio](../docs/audio.md), [vision](../docs/vision.md), and [building](../docs/building.md) guides.

### Differences from the proposal

- **Gamepad slots.** Desktop reads joysticks 1 to 4 into slots 0 to 3 and reports a slot as disconnected when its joystick has no standard mapping. It does not pack the first four mapped joysticks into the slots, so a slot keeps its meaning while another pad comes and goes. Browsers use the pads in the order `navigator.getGamepads()` lists them, skipping those whose mapping is not `standard`. The trigger bits of `GamepadButtons` are set from the analog value, at 128 or more, on both hosts.
- **Touch numbering.** The loop numbers fingers in landing order, starting from 1 again once every finger has lifted. A tap shorter than one tick produces both pointer edges but never appears in `Touches`.
- **Replay format.** The two new flag bits are 14 and 15, which uses the last of the 16 flag bits, so the decoder test for an unknown flag was removed and a test of every rejection of the new lists took its place. The largest possible run is now 232 bytes, and the recorder's reserve per run grew from 94 to 232 bytes. The format version stays 1. A future field needs a version 2.
- **Widgets.** A widget ignores a gamepad button that is already held when it is first updated, so the press that opened a menu does not also activate it. A scene that keeps a menu but stops updating it while hidden must assign a fresh widget when it shows it again. A `Button` is clicked by the south button only while the pointer is over it, because a button has no focus.
- **Sound requests.** The queue holds 64 requests, as proposed. A centered cue is about 3 dB quieter than the M11 mono output, because the equal-power law gives 0.707 to each channel. Ended browser sources stay in the 16-slot ring until a later voice replaces them, because tracking their end would need a Go callback per voice. When a nested runtime's scene exits it clears the shared output, which also stops the outer scene's voices; the guide says so.
- **Parity check.** The browser graph in `scripts/smoke-mixer.mjs` is a copy of the host's voice construction, not shared code, because the host's code runs inside Go WebAssembly. Both files say to keep them in step. The reference is produced by `cmd/mixerref`.
- **Vision.** `Cast` does not know the grid size, so `blocked` must report cells outside the grid as blocked and `visit` can receive such cells. `Field` filters them. A guard that its team sees a scout for wakes only within the 12-tile leash of M13, and an alarmed guard keeps routing toward a hidden scout instead of waiting. An `Attack` order whose target leaves sight ends at once when there is no route to the last seen cell. Every new bolt gets a fired event, including bolts dropped at the board edge. The snapshot is version 1, byte for byte as before, when vision is off, and version 2 when it is on. The explored set and each attacking unit's last seen cell are folded into the trace only when vision is on.
- **Sound and fog.** Sound is positional and does not depend on sight. A guard that is out of sight can be heard, with the gain and pan of its position. This is intended, but it means a player can locate hidden guards by ear. The smoke that the proposal described for hearing a bolt before seeing the guard was not written; a headless test checks that sounds come from events and not from what is drawn.
- **Outpost controls.** The touch buttons are Move, Attack, Hold, and Focus along the bottom of the board, and a Menu button at the top right opens the pause menu. A replay has a Leave button. The pause menu has a Sound entry that steps the volume from full to half to off, because the keys of the outpost have no free letter for a mute key. A pad's cursor, previous buttons, and the touch buttons' visibility are part of the match's hash and snapshot, which is why the snapshot tag is 2. The grid lines are not drawn under fog.
- **Web smoke.** With fog, an attack-move stops for the guards that woke when they saw the scouts, so the scouts no longer cross the alarm line during the Chromium fight. The browser smoke now sends them onto the line with a move order before it uses focus fire. The native smoke, which plays the recorded fight, is unchanged in that respect.
- **Build command.** The default bundle ID is `com.example.NAME`, since there is no real domain to use, and the release workflow passes `-id io.github.krapht-foundation.NAME`. Both versions in `Info.plist` hold only the `X.Y.Z` part, because Apple accepts only numbers there. Archives hold their files at the root with no folder. The tool leaves the Go version check to the `go` command. The release workflow builds each game into its own folder, because two games in one output folder would overwrite each other, and its release job compares the two web zips byte for byte before merging them, which assumes that Go's WebAssembly output is the same on Linux and macOS.
- **Allocation.** The browser polls `navigator.getGamepads()` through `syscall/js`, which allocates a little on every frame; the conversion itself does not.
